## 2. Як рахувалася симуляція

| Поле | Значення |
| --- | --- |
| Інструмент | Власний скрипт моделювання Monte Carlo на Python |
| Прогонів | 10 000 ітерацій |
| Що тягнеться випадково | Фактична velocity одного з моїх спринтів (дискретний вибір із набору [11, 16]) |
| Дата, від якої відлічуються спринти прогнозу | Для сценарію «Весь перший реліз REL-1» — дата старту робіт 2026-10-19; для сценарію «Залишок після двох спринтів» — дата завершення спринта 2 (2026-11-01) |

Логіка моделювання реалізована за алгоритмом Monte Carlo:

```python
import random

def simulate(remaining_points, history, runs=10000):
    sprints_needed = []
    for _ in range(runs):
        points = remaining_points
        sprints = 0
        while points > 0:
            v = random.choice(history)
            points -= v
            sprints += 1
        sprints_needed.append(sprints)
    sprints_needed.sort()
    p50 = sprints_needed[int(runs * 0.50)]
    p85 = sprints_needed[int(runs * 0.85)]
    return p50, p85
```

Чому дати різні: Календарний план за критичним шляхом будується детерміністично на послідовних технологічних зв'язках задач і закладає суворі залежності між етапами тестування та приймання (48 робочих днів). Прогноз Monte Carlo базується на агрегованій швидкості команди в спринтах (velocity), де частина задач розробляється паралельно. Різниця між P85 (14 грудня) та критичним шляхом (23 грудня) становить 9 календарних днів (близько одного робочого тижня). Я вважаю дату критичного шляху більш надійною фінальною межею здачі, а прогноз P85 показує, що розробка функціоналу буде завершена раніше, залишаючи час на спокійне приймальне тестування.

Що я з цим роблю: Я залишаю офіційною датою приймання 2026-12-23 (у межах контракту на 2026-12-25), а випередження за темпом розробки розглядаю як внутрішній буфер команди на випадок затримок зворотного зв'язку від навчальної частини.
